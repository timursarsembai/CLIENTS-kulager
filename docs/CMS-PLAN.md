# План разработки CMS для kulager.kz

Документ описывает, как из нынешнего сайта на файлах-контенте вырастить
самописную CMS с блочным конструктором страниц.

## Исходные условия

- Хостинг — shared (уровня «для WordPress»): Apache + mod_php + `.htaccess` + MySQL.
  Нет Node.js, нет composer, нет консоли, нет фоновых процессов и cron-воркеров.
- Всё, что делает CMS, должно работать в рамках одного HTTP-запроса.
- Языки: русский и казахский.
- Редакторы — не разработчики. Ошибиться в интерфейсе должно быть трудно,
  а сломать вёрстку — невозможно.

## Ключевая идея

Сайт уже собран из блоков: страница — это список
`['type' => 'hero', ...данные]`, а вид задаёт шаблон `views/blocks/{type}.php`.
CMS не меняет эту модель, а лишь переносит источник данных: сейчас массив
приходит из PHP-файла, потом будет приходить из базы. Рендер, вёрстка и
шаблоны остаются теми же.

Отсюда главное ограничение конструктора, и его стоит принять сознательно:
**редактор собирает страницу из готовых блоков и заполняет их поля,
но не рисует произвольную вёрстку.** Это не Elementor с холстом и
перетаскиванием пикселей — это конструктор из фирменных секций. Дизайн
остаётся целостным, редактор не может получить «поехавшую» страницу, а объём
работ сокращается в разы. Свободную вёрстку внутри блока даёт только
`richtext`-поле.

## Модель данных

```
users            id, email, password_hash, role, created_at, last_login_at
pages            id, key, template, parent_id, sort, status, created_at, updated_at
page_locales     page_id, locale, slug, title, description, og_image, bar_json, is_published
page_blocks      id, page_id, locale, sort, type, data_json, is_visible
page_revisions   id, page_id, locale, author_id, snapshot_json, comment, created_at
media            id, path, mime, width, height, size, alt_ru, alt_kk, created_at
navigation       id, key, locale, sort, parent_id, title, url, page_id
settings         key, locale, value_json
login_attempts   ip, attempted_at            (защита от подбора пароля)
```

Решения, которые стоит зафиксировать:

- `data_json` — обычный `TEXT` с `json_encode`, а не тип `JSON`: на shared-хостинге
  версия MariaDB заранее не известна, а выборки внутри JSON нам не нужны.
- Блоки хранятся **по языкам отдельно** (`page_blocks.locale`). Русская и
  казахская страницы могут расходиться по набору блоков — это нормально.
- `page_revisions` пишется при каждой публикации целиком. Откат — это вставка
  снапшота обратно. Просто, надёжно, без diff-логики.
- Никаких ORM. Тонкий слой над PDO с подготовленными запросами.

## Реестр блоков

Сердце конструктора — декларативное описание полей каждого блока.
Из него генерируются и форма редактирования, и валидация, и значения
по умолчанию:

```php
'cards' => [
    'title' => 'Карточки',
    'group' => 'Контент',
    'fields' => [
        'kicker' => ['type' => 'string', 'label' => 'Надзаголовок'],
        'title'  => ['type' => 'string', 'label' => 'Заголовок', 'required' => true],
        'lead'   => ['type' => 'text',   'label' => 'Лид'],
        'panel'  => ['type' => 'bool',   'label' => 'На подложке'],
        'items'  => ['type' => 'list',   'label' => 'Карточки', 'of' => [
            'title' => ['type' => 'string', 'label' => 'Заголовок'],
            'text'  => ['type' => 'text',   'label' => 'Описание'],
        ]],
        'actions' => ['type' => 'list', 'label' => 'Кнопки', 'of' => 'action'],
    ],
],
```

Типы полей: `string`, `text`, `richtext`, `bool`, `number`, `select`, `image`,
`link`, `action`, `list` (повторяющаяся группа), `blocks` (вложенные блоки —
пока не нужно).

Так новый тип блока добавляется тремя шагами: шаблон в `views/blocks/`,
описание полей в реестре, запись в CSS. Админку править не нужно.

## Этапы

### Этап 1. Фундамент — сделано

- Слой БД на PDO, конфиг подключения, единая обработка ошибок.
- Свои миграции: `app/migrations/001_init.php`, счётчик применённых
  в таблице `migrations`, запуск из админки (консоли на хостинге нет).
- Базовый слой безопасности: CSRF-токены, экранирование, единая точка
  проверки прав.

### Этап 2. Вход и каркас админки — сделано

- `/admin` с собственным front-controller и своим `.htaccess`.
- Вход по email + `password_hash()`, сессии `httponly` + `samesite=strict`,
  задержка и блокировка после серии неудачных попыток.
- Роли: администратор (всё) и редактор (контент без настроек и пользователей).
- Каркас интерфейса: список страниц, шапка, навигация. Верстаем на том же
  CSS-подходе, без сборки и фреймворков.

### Этап 3. Хранилище контента и перенос текущего — сделано

- Репозитории `PageRepository`, `BlockRepository`.
- `Router` берёт страницу из БД, а при отсутствии — из файлов `content/`
  (как сейчас). Файлы остаются рабочим резервом на время переезда.
- Скрипт-импортёр: раскладывает нынешние `content/*.php` по таблицам.
  Главная, отрасль и обе модели переезжают без ручного ввода.

### Этап 4. Реестр блоков и генератор форм — сделано

- Описание полей для всех существующих типов (19 блоков).
- Генератор формы по описанию, включая повторяющиеся группы (`list`)
  с добавлением, удалением и перестановкой элементов.
- Валидация и приведение типов на сервере — клиентской проверке не доверяем.

### Этап 5. Редактор страницы — сделано

Это и есть конструктор:

- Список блоков страницы: перестановка перетаскиванием (порядок сохраняется
  сам), скрытие с сайта без удаления, копирование, удаление.
- Добавление блока из библиотеки — она собрана из реестра и сгруппирована
  по назначению, у каждого типа своя подсказка.
- Поля блока правятся на отдельной странице формы. Боковую панель не делали:
  у некоторых блоков полей много, в узкой колонке они не помещаются.
- Настройки страницы: адрес, мета-теги, картинка для соцсетей, тексты
  плавающей панели. Публикация и снятие с публикации — там же.
- Предпросмотр — та же публичная страница с `?preview=1`, а не отдельный
  рендер: показывает ровно то, что увидит посетитель. Гостю черновик
  не отдаётся.

Drag-and-drop и `richtext` — ванильный JS: `contenteditable` плюс кнопки
(жирный, курсив, список, ссылка), вставка только текстом. HTML чистится
на сервере по белому списку тегов, `javascript:` в ссылках отбрасывается.

Чего сознательно не делали: автосохранения полей на лету. Форма сохраняется
кнопкой — так редактор всегда понимает, записаны его правки или нет.

### Этап 6. Медиатека — сделано

- Тип файла определяется по содержимому (`finfo` + `getimagesize`), присланное
  имя в решении не участвует. Имя файла собирается заново, кириллица
  транслитерируется.
- Растровые картинки пересохраняются через GD — это отбрасывает всё лишнее,
  что могло быть спрятано внутри файла. Заодно готовятся копии 480/960/1600 px.
- SVG через GD не проходит: это разметка. Файлы со скриптами, обработчиками
  событий и ссылками на чужие серверы отклоняются целиком.
- `uploads/.htaccess` запрещает выполнение кода несколькими способами сразу
  (проверено: PHP-файл в каталоге отдаёт 403).
- Поле `image` в формах открывает медиатеку отдельным окном и получает путь
  обратно; alt хранится на двух языках.
- Если на хостинге нет GD, загрузка продолжает работать — просто без
  уменьшенных копий.

### Этап 7. Языки — сделано

- Переключение языка в редакторе, копирование блоков основного языка
  в другой одной кнопкой — как заготовка для перевода.
- Подсказка о состоянии перевода: сколько блоков дословно совпадает
  с основным языком, то есть ещё не переведено.
- Откат на основной язык теперь работает и из базы, а не только из файлов:
  если казахской версии нет или в ней нет блоков, показывается русская.
  Страница не пропадает из-за незаконченного перевода.

### Этап 8. Кэш страниц — 1–2 дня, делаем только при необходимости

Замер на текущем сайте: сборка главной из блоков занимает **9 мс** и 2 МБ
памяти, страница целиком отдаётся за 7 мс. Это дёшево. Даже если shared-хостинг
окажется втрое медленнее, речь идёт о десятках миллисекунд — посетитель
разницы не заметит.

Поэтому кэш сразу не делаем. Он понадобится, если на боевом хостинге
страницы будут отвечать заметно медленнее (скажем, дольше 300 мс) или
появится ощутимый трафик. Тогда схема такая:

- При публикации страница один раз рендерится в файл `cache/{locale}/{slug}.html`.
- `.htaccess` отдаёт этот файл напрямую, минуя PHP, — как обычную картинку.
- Публикация любой страницы удаляет связанные файлы, следующий посетитель
  получает свежую версию.
- Авторизованный редактор всегда видит живую страницу, а не кэш.

Это то же самое, что делают плагины кэширования в WordPress, только
встроенное и без лишних настроек.

### Этап 9. Настройки и SEO — сделано

- Раздел «Настройки»: телефон, WhatsApp, почта, режим работы, адреса.
  Меняются без разработчика и подставляются во все страницы сразу, включая
  микроразметку. Пустое поле означает «взять значение из конфига», поэтому
  сайт работает и до переноса настроек.
- Мета-теги и картинка для соцсетей правятся на самой странице (этап 5).
- `robots.txt` и `sitemap.xml` отдаются из PHP: карта собирается из
  опубликованных страниц с `hreflang`, а не из файла, который надо
  перегенерировать. Планировщика на хостинге нет, так что это надёжнее.

**Меню осталось на файлах** (`content/navigation.ru.php`). Причина: 22 отрасли
и модели удобнее строить из самих страниц, а не поддерживать вторым списком.
Это делается вместе с созданием остальных отраслей — иначе редактор будет
вручную дублировать то, что и так есть в базе.

### Этап 10. Эксплуатация — сделано

- Выгрузка копии одной кнопкой: дамп базы и каталог загрузок в архиве.
  Дамп собирается запросами и отдаётся потоком — `mysqldump` на хостинге нет,
  а в память копия не помещалась бы. Без ZipArchive выгружается только дамп.
- Журнал действий: кто вошёл, что опубликовал, что удалил, когда менял
  настройки. С постраничной навигацией.
- Страница «Состояние»: версия PHP, расширения, лимиты, права на каталоги,
  применённые миграции — диагностика хостинга без консоли.

## Что уже готово

Этапы 1–5 закрыты: база и миграции, вход в админку, хранилище контента
с переносом из файлов, реестр блоков с описанием полей и редактор страницы.
Контент правится через админку без участия разработчика.

Проверено на реальном контенте: все 59 блоков четырёх страниц прошли через
формы редактора туда и обратно — ни одно поле не потерялось, страницы
посимвольно совпадают с исходными макетами.

Этап 6 (медиатека) закрыт: загрузка с проверкой содержимого, защита каталога
от выполнения кода, уменьшенные копии, выбор картинки из формы.

Этапы 7, 9, 10: языки в редакторе, настройки сайта, `robots.txt` и
`sitemap.xml`, резервные копии, журнал действий.

**Все запланированные этапы закрыты, кроме двух отложенных по делу:**

- этап 8 (кэш страниц) — замеры показывают, что не нужен: сборка страницы
  занимает 9 мс. Вернуться, если на хостинге будет медленно;
- редактор меню — привязан к созданию остальных 21 отрасли, иначе редактор
  будет поддерживать список дважды.
Минимально работающий вариант — этапы 1–5 (редактор страниц), это
13–17 дней; остальное можно добавлять по мере надобности.

Форм обратной связи на сайте не будет: все обращения идут в WhatsApp
(решение от 18.08.2026). Если понадобятся позже — это отдельный блок `form`,
таблица заявок и раздел в админке, около двух дней.

## Что важно не упустить

- **Публичная часть не должна зависеть от админки.** Даже если `/admin`
  сломан или удалён, сайт продолжает отдавать страницы.
- **Резерв на файлах.** Пока контент не переехал целиком, `content/*.php`
  остаются рабочим источником — переезд можно делать постранично.
- **Никаких зависимостей.** Всё, что добавляем, должно работать на голом
  PHP 8 с расширениями `pdo_mysql`, `gd`, `fileinfo`, `mbstring`.
- **Ограничения хостинга.** `upload_max_filesize`, `max_execution_time` и
  права на запись проверяем на странице «Состояние», а не ловим в проде.
- **Резервные копии до переезда.** Перед импортом контента в базу — выгрузка
  файлов, чтобы откат был возможен.
