# KULAGER — корпоративный сайт

Чистый PHP 8 без фреймворка и без сборки: проект рассчитан на обычный
shared-хостинг (Apache + mod_php + `.htaccess`, MySQL), где нельзя запустить
Node.js или Laravel. Composer не требуется — зависимостей нет.

## Структура

```
public_html/          ← заливается в корень сайта (DocumentRoot)
  index.php           единая точка входа сайта
  .htaccess           ЧПУ, сжатие, кэш, заголовки безопасности
  admin/              админка: своя точка входа и свой .htaccess
  assets/
    css/site.css      стили сайта
    css/admin.css     стили админки
    css/edit.css      правка текста на странице
    js/site.js        темы, меню, панель призыва, счётчики
    js/edit.js        правка текста на странице
    img/              иконки и изображения

app/                  ← кладётся уровнем выше public_html, из веба недоступен
  init.php            общая инициализация сайта и админки
  bootstrap.php       запуск публичной части
  config.php          контакты, языки, доступ к БД
  routes.php          карта страниц: адрес → шаблон
  themes.php          цветовые темы «из коробки» (дальше правятся в админке)
  sections.php        разделы страниц: отрасли, модели, основные
  blocks.php          реестр блоков: описание полей каждого типа
  migrations/         миграции схемы БД
  logs/               журнал ошибок, закрыт от веба
  cache/              готовые страницы, чистится сама
  src/                Site, Router, View, Db, Auth, Blocks, Admin, …
  content/            контент страниц и навигация (резерв для базы)
  views/
    layout.php        каркас документа
    pages/            страницы
    blocks/           блоки контента — по одному шаблону на тип
    partials/         шапка, подвал, меню, кнопки, микроразметка
    admin/            экраны админки

docker/               локальное окружение, на хостинг не заливается
_import/              исходники из Claude Design, справочно
```

`index.php` ищет `app/` сначала рядом с `public_html`, затем внутри него —
работает при любой раскладке хостинга. Если каталог всё же оказался внутри
корня сайта, он закрыт своим `.htaccess` и правилом в `public_html/.htaccess`.

## Как устроен контент

Страница — это список блоков. Каждый блок знает свой тип и данные,
а внешний вид задаёт шаблон `views/blocks/{type}.php`:

```php
'blocks' => [
    ['type' => 'hero',   'title' => '...', 'image' => '...'],
    ['type' => 'cards',  'items' => [...]],
]
```

Так же работает конструктор страниц в админке: редактор меняет порядок
и настройки блоков, а на выходе получается ровно такой массив. Основной
источник — база; файлы `app/content/*.php` остаются резервом.

Какие поля есть у каждого типа блока, описано в `app/blocks.php`. Из этого
описания строятся и форма редактирования, и проверка значений — поэтому новый
тип блока добавляется тремя шагами: шаблон в `views/blocks/`, описание полей
в реестре, стили в CSS. Админку править не нужно.

Готовые типы блоков: `hero`, `page_head`, `product_hero`, `platform`, `solutions`, `gov`,
`photo_band`, `models`, `stats`, `compare`, `spec_compare`, `spec_table`,
`service`, `cards`, `steps`, `testdrive`, `split_cta`, `cta_box`, `lead`,
`industries`.

Универсальнее прочих `cards`: заголовок, сетка карточек и необязательные
кнопки. Карточка с заполненным полем «Ссылка» кликается целиком — так собран
каталог отраслей. Им описаны «Запчасти», «Магазин», «Документы», «Доставка», «Задачи»,
«Сезоны» и «Сертификаты» — один шаблон на семь секций.

Блоки, повторяющиеся на всех внутренних страницах (платформа, решения,
госсектор, документы, запчасти, магазин, отрасли), лежат в
`content/shared.ru.php`. Страница вставляет их в свой список, а отличия
задаёт через `array_replace()` — правка текста расходится сразу на все
страницы, но частный случай можно переопределить.

## Шаблонные маршруты

Отрасли и модели описаны в `routes.php` одной строкой каждая:

```php
'industry' => ['slug' => ['ru' => 'otrasli/{slug}'], 'content_dir' => 'industries'],
```

Адрес подходит, если для него есть файл контента
(`content/industries/<slug>.ru.php`) — иначе страница отдаёт 404. Чтобы
добавить отрасль, достаточно положить файл: маршрут, `hreflang` и переключатель
языка подхватятся сами.

Готовы главная, 22 отрасли, обе модели, «Все отрасли применения», «О компании»,
«Обратная связь», «Реквизиты» и «Дилерам» — **на двух языках**. Файлы контента
собраны из макетов Claude Design автоматически: разбор шёл по секциям, а общие
для всех блоки подставлены из `shared.{язык}.php`. Каждая страница сверена
с макетом построчно (`verify.py`): расхождений нет ни на одной из 56 языковых
версий, битых внутренних ссылок на сайте нет.

Отраслей 22 — все на месте. У **животноводческих ферм** нет фирменного
макета: в дизайн-проекте файл `zhivotnovodcheskie-fermy.dc.html` содержит текст
страницы акиматов. Страница написана по образцу соседних отраслей, поэтому
`verify.py` её не сверяет — сверять не с чем.

### Чего на сайте намеренно нет

Магазин запчастей, сервисный центр, личный кабинет и ERP остаются
демонстрационными макетами — страниц под них пока нет. Поэтому из меню, подвала
и контента убраны ссылки на «Магазин запчастей», «Сервисный центр», «Условия
гарантии», «Регламент ТО», «Публичную оферту» и «Политику конфиденциальности».
Сами тексты в макетах сохранились: когда страницы появятся, ссылки вернутся
в `content/navigation.{язык}.php`.

Казахская «Дилерам» переведена и лежит в `content/dileram.kk.php`. Структура
взята из русской версии: казахский макет этой страницы сделан по старому
дизайну и короче, поэтому построчная сверка с ним неприменима — `verify.py`
её пропускает. Формулировки дилерских блоков взяты из казахского макета,
остальные — те же, что на отраслевых страницах.

## Языки

Основной язык (`ru`) живёт в корне, остальные — под своим префиксом: `/kk/...`.
Адреса страницы на разных языках задаются в `app/routes.php`, из них же
строятся `hreflang` и переключатель языка.

Контент ищется по имени `content/{страница}.{язык}.php`. Если перевода ещё
нет, показывается версия на основном языке — страница не ломается.

Строки интерфейса (шапка, подвал, боковое меню) лежат отдельно в `app/lang/`:
в контенте страниц их нет, а переводить надо. Навигация — своя на каждый язык
(`content/navigation.{язык}.php`), адреса при этом общие.

Казахские макеты короче русских на один блок: секции «Интернет-магазин
запчастей» в них нет, поэтому её нет и на казахских страницах.

## Админка

Открывается по адресу `/admin`. При первом заходе она сама проведёт через
установку: применит миграции базы и предложит создать администратора.
Пока пользователя нет, попасть внутрь нельзя.

Оформлена в фирменном стиле сайта: светлая тема «Фарфор», заголовки Oswald,
подписи полей и метки — мелким шрифтом с разрядкой, как надзаголовки на
страницах. Углы прямые, карточки плоские с тонкой рамкой, список блоков
выложен сеткой с линиями — тем же приёмом, что и карточки отраслей. В шапке
логотип из настроек, перекрашенный темой.

Цвета берутся из той же таблицы тем, что и на сайте: если поправить «Фарфор»
в разделе «Оформление», изменится и вид самой админки.

Раздел «Состояние» показывает версию PHP, наличие нужных расширений, лимиты
и права на запись — на shared-хостинге консоли нет, а диагностировать надо.
Там же кнопка переноса контента из файлов `app/content` в базу.

### Редактор страницы

Страница правится списком блоков: перетащить за ручку, чтобы поменять
порядок (сохраняется сам), скрыть с сайта без удаления, скопировать, удалить.
Новый блок добавляется из библиотеки справа — она собрана из реестра
`app/blocks.php`, поэтому новый тип блока появляется там сам.

Поля блока правятся на отдельной странице. Форма строится по описанию из
реестра: подписи, подсказки, обязательные поля, повторяющиеся группы
(например список карточек) с добавлением и перестановкой. Всё присланное
проверяется на сервере — то, чего нет в схеме, отбрасывается.

Предпросмотр черновика — это обычная страница сайта с `?preview=1`: видно
ровно то, что увидит посетитель. Гостю черновик не отдаётся.

Снятая с публикации страница отдаёт 404, даже если для неё остался файл
в `app/content` — решение редактора важнее резерва.

**Отменить.** Перед каждым изменением блоков — правкой, удалением, копированием
из основного языка, настройками страницы, правкой на самом сайте — снимается
слепок языковой версии. Кнопка «Отменить» вверху редактора возвращает страницу
к состоянию до последнего изменения и подписана тем, что именно отменяет.
Снимков храним пятнадцать на языковую версию, лишние удаляются сами.

Особенно это нужно кнопке «Заново скопировать из основного языка»: она заменяет
блоки перевода копией русских, и без отмены готовый перевод пришлось бы
набирать заново.

### Правка текста на странице

Из редактора страницы есть ссылка «править на сайте» — она открывает обычную
страницу с `?edit=1`. Помеченные тексты (заголовки, вводные абзацы, карточки,
шаги, призывы) становятся редактируемыми: щёлкнули, поправили, ушли с поля —
сохранилось. Enter завершает правку, Escape отменяет.

Работает это только для вошедшего редактора и только для страниц из базы:
у блоков из файлов нет идентификаторов, сохранять правку было бы некуда.
Значение не пишется как есть — данные блока собираются заново и проходят
`Blocks::sanitize()`, ту же проверку, что и форма в админке. Если поле
обязательное и его очистили, правка не сохранится, а текст вернётся на место.

Размечены все 20 типов блоков — от обложки до таблиц характеристик и реквизитов.
Правятся не только заголовки и абзацы, но и подписи кнопок и ссылок, метки,
пометки, значения характеристик и строки таблиц.

Поля с разметкой (заголовок обложки с переносом строки, сноска под таблицей,
контакты в блоке заявки) помечаются третьим доводом `'html'`: в них Enter
делает перенос строки, а лишние теги срезает `Blocks::cleanHtml()` — скрипты
и стили вырезаются вместе с содержимым.
Разметка задаётся в шаблонах помощником `$view->editable($block, 'путь')`,
где путь — расположение поля в данных блока (`items.0.title`). Вне режима
правки помощник возвращает пустую строку, поэтому обычная страница не меняется
ни на байт.

Правится не только контент блоков. На странице редактируются:

- **пункты меню** — названия отраслей в блоке «Отрасли применения», ссылки
  в подвале и в боковом меню;
- **строки интерфейса** — подписи в подвале и боковом меню («Работа и адреса»,
  «Модели», строка под логотипом). Правка сохраняется поверх файлов `app/lang`,
  отдельно для каждого языка;
- **контакты** — телефон и почта в подвале пишутся в настройки сайта;
- **плавающая панель внизу** — её тексты хранятся в самой странице.

**Подвал и боковое меню разделены.** Пункт остаётся один — иначе отрасль
пришлось бы переименовывать дважды, — но у него есть отдельное название
для подвала и признак показа. Пока название для подвала не заполнено, там
используется общее; как только его правят прямо в подвале, оно отвязывается
и боковое меню не меняется. Оба поля видны в разделе «Меню».

Поля, которых на странице не видно — заголовок для поиска, стиль кнопки,
подложка секции, — правятся, как и раньше, в админке.

### Медиатека

Раздел «Медиатека»: загрузка изображений, описания на двух языках, удаление.

Из любой формы картинка выбирается кнопкой «Выбрать»: поверх страницы
открывается окно с двумя вкладками — библиотека и загрузка. Файл, загруженный
во вкладке «Загрузить» (кнопкой или перетаскиванием), сразу подставляется
в поле, страница при этом не перезагружается. Так работают и картинки блоков,
и галереи, и картинка страницы для соцсетей.

Тип файла определяется по содержимому, а не по расширению: PHP-скрипт,
переименованный в `.png`, не пройдёт. Растровые картинки пересохраняются
через GD, попутно создаются копии 480/960/1600 px. SVG проверяется на скрипты
и внешние ссылки. Каталог `assets/uploads` закрыт от выполнения кода — этому
нужен рабочий `.htaccess`, проверьте после переезда на хостинг.

Каталогу `assets/uploads` нужны права на запись (755 или 775).

### SEO

Раздел «SEO» (только для администратора) задаёт то, что подставляется страницам
без своих значений: название сайта для соцсетей, приписку к заголовку вкладки
(добавляется, только если её ещё нет в заголовке), описание и картинку
по умолчанию, коды подтверждения прав в Яндексе и Google, дополнительные
строки robots.txt.

Переключатель «Закрыть весь сайт от индексации» нужен на время доработки:
во все страницы добавляется `noindex`, robots.txt запрещает обход, карта сайта
отдаётся пустой. В админке при этом висит заметное предупреждение.

Ниже — сводка по всем языковым версиям: длина заголовка и описания, чего
не хватает, что закрыто от индексации, что осталось черновиком. Проверять
шесть десятков страниц вручную никто не станет, а так видно за один взгляд.

У каждой страницы в её настройках есть «Закрыть от индексации» (страница
остаётся на сайте, но пропадает из карты сайта и поиска) и «Канонический
адрес» — на случай, когда содержимое дублирует другую страницу.

### Настройки сайта

Раздел «Настройки»: телефон, WhatsApp, почта, режим работы, адреса. Меняются
без разработчика и подставляются сразу во все страницы, включая микроразметку
для поисковиков. Пустое поле означает «взять значение из `app/config.php`»,
поэтому сайт работает и до заполнения настроек.

### Языки в редакторе

У каждой страницы свои блоки для каждого языка. Кнопка в редакторе копирует
блоки основного языка в другой — дальше остаётся заменить текст на перевод.
Рядом видно, сколько блоков ещё дословно совпадает с основным языком.

Если перевода нет вовсе или в нём нет блоков, посетителю показывается версия
на основном языке: страница не пропадает из-за незаконченного перевода.

### Меню

Раздел «Меню»: пункты каждого меню правятся списком, порядок меняется
перетаскиванием, ссылка выбирается из списка страниц. Меню отраслей устроено
группами — «АПК», «Коммунальное хозяйство», «Бизнес», внутри каждой свои
пункты. У каждого языка своё меню, адреса при этом общие.

Меню лежит в базе; файлы `content/navigation.{язык}.php` остаются резервом
и источником для переноса — он делается кнопкой «Перенести контент в базу»
вместе со страницами.

### Оформление

Раздел «Оформление» (только для администратора): пять готовых тем — Кобальт,
Фарфор, Песок, Графит, Хаки — и свои.

Переменные разбиты на группы, и у каждой написано, где её видно на сайте:
«Основные цвета» (фон, текст, акцент — обычно правят только их), «Подложки
и карточки», «Оттенки текста», «Линии и рамки», «Полупрозрачные слои»
и «Дополнительно». Полупрозрачные слои — шапка, панель внизу, затемнение
обложки — задаются пипеткой и ползунком прозрачности: `rgba(...)` собирается
сам. Справа предпросмотр, обновляется сразу.

Новая тема создаётся копией существующей: три десятка переменных с нуля
никто не заполняет. Встроенные темы удалить нельзя — на них ссылается конфиг.
Тема по умолчанию задаётся тут же, посетитель может переключить её сам.

Файл `app/themes.php` остаётся набором «из коробки»: из него делается первое
наполнение таблицы и запасной вариант, если база недоступна.

### Кэш страниц

Готовая страница сохраняется в `app/cache` и следующему посетителю отдаётся
без обращения к базе и сборки блоков — по замерам это втрое быстрее. Кэш
не используется для POST-запросов, адресов с параметрами и для тех, у кого
есть сессия: редактор всегда видит живую страницу.

Сбрасывается сам при любой правке в админке — не удалением файлов, а сменой
версии: каждая версия лежит в своём подкаталоге `cache/v…`, прошлые убираются
при следующих записях. Кнопка «Сбросить кэш» в разделе «Состояние» нужна,
только если данные меняли мимо админки. Каталогу `app/cache` нужны права
на запись, как и `assets/uploads`.

### Заявки

Блок «Форма заявки» ставится на любую страницу из библиотеки блоков: имя,
телефон, почта, сообщение. Заявка **сначала сохраняется в базу и только потом
уходит в телеграм** — если бот недоступен, обращение не потеряется, а в списке
будет пометка «не ушло» и кнопка отправить повторно.

Форма работает и без JavaScript: тогда она отправляется обычным POST и
возвращает на страницу с сообщением. Со скриптом — без перезагрузки.

Защита от роботов рассчитана на кэшируемые страницы, поэтому вместо
CSRF-токена из сессии:

- подпись формы, которая меняется раз в сутки;
- спрятанное поле-ловушка — люди его не видят и не заполняют;
- отметка времени показа формы (её ставит скрипт, не сервер: страница
  из кэша у всех одна);
- не больше пяти заявок с одного адреса в час.

**Телеграм** настраивается внизу раздела «Заявки»: токен от @BotFather и чат.
Чат определяется кнопкой — достаточно написать боту «/start». Рядом кнопка
проверочного сообщения. Токен хранится только в базе и в интерфейсе больше
не показывается.

### Счётчики

В разделе «SEO» есть карточка «Счётчики и аналитика». Для Яндекс.Метрики
и Google Analytics достаточно номера — код собирается сам и ставится куда
нужно. Для остальных сервисов есть поля со свободным кодом: в `<head>`
и перед `</body>`.

Важная деталь: политика безопасности запрещает чужие скрипты, поэтому домены
включённых счётчиков добавляются в неё автоматически (`Counters::hosts()`).
Если свой счётчик грузится со стороннего домена, его нужно вписать в поле
«Разрешить домены» — иначе браузер его заблокирует. Из-за этого политика
публичной части задаётся из PHP (`bootstrap.php`), а не из `.htaccess`:
файл о настройках не знает.

Редактору счётчики не подключаются — собственные заходы считать незачем.

### Панель администратора

Тому, кто вошёл в админку, на всех страницах сайта показывается тёмная полоса
сверху: переход в редактор именно этой страницы, включение и выключение правки
текста, ссылки на заявки и медиатеку. Гость её не получает — в разметке её
нет вовсе, и страницы для гостей кэшируются без неё.

### Пользователи

Раздел «Пользователи» (только для администратора): кто заведён, с какой ролью,
когда входил последний раз. Новому пользователю пароль придумывает система
и показывает один раз — передать его нужно лично, а человек сменит пароль
в своём профиле.

Роли две. **Администратор** меняет всё: настройки, SEO, темы, перенос контента,
самих пользователей. **Редактор** работает только с контентом — страницы,
блоки, меню, медиатека.

Тут же: сброс пароля, сброс входа по коду (если человек потерял телефон),
закрытие доступа без удаления (правки в журнале остаются связанными с ним)
и удаление. Система не даст понизить, отключить или удалить последнего
администратора и не даст закрыть доступ самому себе.

### Безопасность

Вход в админку защищён так:

- пароли хранятся только хешами (`password_hash`), при входе хеш считается
  даже для несуществующей почты — по времени ответа не понять, заведён такой
  пользователь или нет;
- после десяти неудачных попыток за 15 минут вход блокируется — и по адресу,
  с которого подбирают, и по самой почте: сотня адресов на один аккаунт лимит
  по IP не превысила бы;
- сессия привязана к строке браузера, закрывается через два часа без действий
  и через двенадцать часов в любом случае;
- все изменяющие запросы проверяются на CSRF-токен, cookie сессии — `HttpOnly`,
  `SameSite=Strict`, а по HTTPS ещё и `Secure`;
- админка отдаёт свою политику безопасности (CSP) с одноразовым ключом:
  выполняются только свои скрипты, чужой — вставленный в текст страницы —
  не запустится. У сайта политика попроще: она запрещает подгрузку скриптов
  и фреймов с чужих доменов;
- входы, неудачные попытки и блокировки пишутся в журнал действий.

**Вход по одноразовому коду** (двухфакторный) включается в разделе «Профиль»:
ключ добавляется в приложение-аутентификатор (Google Authenticator, Aegis,
1Password), после чего админка после пароля спрашивает шестизначный код.
Заодно выдаются десять запасных кодов на случай потери телефона — каждый
срабатывает один раз. Реализация своя (`app/src/Totp.php`, RFC 6238),
сверена с контрольными векторами стандарта.

Сводка — в разделе «Состояние»: HTTPS, отладка, у кого включён второй шаг,
сколько неудачных входов за сутки.

### Резервные копии и журнал

На странице «Состояние» — кнопка выгрузки копии: дамп базы и каталог загрузок
одним архивом. Дамп собирается запросами и отдаётся потоком, `mysqldump`
на хостинге не нужен. Шаблоны и стили в копию не входят — они в исходниках.

Журнал действий показывает, кто вошёл, что опубликовал, что удалил и когда
менял настройки.

### robots.txt и sitemap.xml

Отдаются из PHP по адресам `/robots.txt` и `/sitemap.xml`. Карта сайта
собирается из опубликованных страниц с `hreflang` — то есть всегда актуальна
и не требует перегенерации.

Как устроен доступ:

- пароли — только `password_hash()`, десять неудачных попыток с адреса
  за 15 минут временно закрывают вход;
- сессия привязана к строке браузера, cookie `httponly` + `SameSite=Strict`;
- каждая изменяющая форма проверяется CSRF-токеном;
- публичная часть работает без сессий — иначе её нельзя было бы кэшировать.

Контент берётся из базы, а если она недоступна или страница ещё не перенесена —
из файлов `app/content`. Это проверено: при остановленной базе сайт продолжает
отдавать страницы.

## Локальная разработка

```bash
docker compose up -d --build   # http://127.0.0.1:8090
docker compose logs -f web
docker compose down
```

Окружение повторяет хостинг: Apache с `mod_rewrite` и `.htaccess`.

## Выкладка на хостинг

1. Содержимое `public_html/` — в корень сайта.
2. Каталог `app/` — уровнем выше корня (если хостинг не даёт — рядом с `index.php`).
3. В `app/config.php` проставить `base_url`, доступы к базе (`db`) и оставить
   `debug => false`.
4. Дать права на запись каталогам `app/logs` и `public_html/assets/uploads`.
5. Открыть `/admin` — там применить миграции и создать администратора.

`docker/`, `_import/` и `README.md` на хостинг не нужны.
